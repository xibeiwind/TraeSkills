本文档提供了 NestJS 项目的全面代码审查检查清单，涵盖架构设计、代码质量、性能、安全和最佳实践等多个维度。

## 架构设计

### 模块化设计
- [ ] **模块职责单一性**
  - 每个模块是否只负责一个明确的业务领域
  - 模块边界是否清晰，避免循环依赖
  - 模块是否遵循单一职责原则（SRP）

- [ ] **模块依赖关系**
  - 依赖方向是否正确（低层模块不应依赖高层模块）
  - 是否存在循环依赖
  - 共享模块（SharedModule）的使用是否合理

- [ ] **模块导出控制**
  - 模块导出的内容是否经过严格筛选
  - 是否导出了不必要的内部实现细节
  - 是否正确使用 `@Global()` 装饰器（仅在必要时）

### 分层架构
- [ ] **Controller 层**
  - Controller 是否仅负责 HTTP 请求处理和响应
  - 是否包含业务逻辑（应移至 Service 层）
  - DTO（数据传输对象）的使用是否规范
  - 请求验证是否使用 class-validator

- [ ] **Service 层**
  - Service 是否包含核心业务逻辑
  - 是否避免直接操作 HTTP 请求/响应对象
  - 异常处理是否合理
  - 事务管理是否正确

- [ ] **Repository/DAO 层**
  - 数据访问逻辑是否与业务逻辑分离
  - 是否正确使用 TypeORM 或其他 ORM
  - 查询优化是否考虑（N+1 问题）
  - 数据库连接管理是否正确

### 依赖注入
- [ ] **依赖注入模式**
  - 是否正确使用 NestJS 依赖注入系统
  - Provider 的作用域（DEFAULT、REQUEST、TRANSIENT）是否合理
  - 循环依赖是否通过 `forwardRef()` 正确处理

- [ ] **接口与实现分离**
  - 是否为关键服务定义接口
  - 依赖是否基于接口而非具体实现
  - 是否便于测试和替换实现

## 代码质量

### 代码风格
- [ ] **命名规范**
  - 类名使用 PascalCase（如 `UserService`）
  - 方法名和变量名使用 camelCase（如 `getUserById`）
  - 常量使用 UPPER_SNAKE_CASE（如 `MAX_RETRY_COUNT`）
  - 私有成员使用下划线前缀（如 `_internalMethod`）

- [ ] **代码格式化**
  - 是否使用 Prettier 或 ESLint 统一代码格式
  - 缩进、空格、换行是否一致
  - 行长度是否合理（建议不超过 120 字符）

- [ ] **注释质量**
  - 复杂逻辑是否有清晰的注释说明
  - 注释是否准确反映代码意图
  - 是否避免无意义的注释（如 `// 获取用户`）
  - 是否使用 JSDoc 为公共 API 提供文档

### 类型安全
- [ ] **TypeScript 使用**
  - 是否避免使用 `any` 类型
  - 是否正确使用接口和类型定义
  - 泛型的使用是否合理
  - 类型断言是否必要且安全

- [ ] **空值处理**
  - 是否正确处理可能为 null/undefined 的值
  - 是否使用可选链操作符（`?.`）和空值合并操作符（`??`）
  - 是否使用 strictNullChecks 模式

### 错误处理
- [ ] **异常处理策略**
  - 是否使用 NestJS 内置异常类（如 `HttpException`、`BadRequestException`）
  - 自定义异常是否继承基础异常类
  - 异常信息是否包含足够的调试信息但不泄露敏感数据

- [ ] **全局异常过滤器**
  - 是否实现了全局异常过滤器
  - 异常响应格式是否统一
  - 是否正确记录异常日志

- [ ] **异步错误处理**
  - Promise 是否正确处理 rejection
  - async/await 是否正确使用 try-catch
  - 是否避免未捕获的 Promise rejection

## 性能优化

### 数据库性能
- [ ] **查询优化**
  - 是否避免 N+1 查询问题
  - 是否正确使用索引
  - 是否使用查询构建器优化复杂查询
  - 是否使用缓存机制（Redis 等）

- [ ] **连接管理**
  - 数据库连接池配置是否合理
  - 是否正确关闭数据库连接
  - 事务范围是否最小化

### 缓存策略
- [ ] **缓存实现**
  - 是否使用 NestJS CacheModule
  - 缓存键设计是否合理
  - 缓存失效策略是否正确
  - 是否考虑缓存穿透、缓存雪崩问题

### 异步处理
- [ ] **异步任务**
  - 长时间运行的任务是否使用队列（Bull、BullMQ）
  - 是否正确处理并发和竞态条件
  - 是否使用适当的并发控制

### 资源管理
- [ ] **内存管理**
  - 是否避免内存泄漏
  - 大数据集是否使用流式处理
  - 是否正确释放资源（文件句柄、连接等）

## 安全性

### 认证与授权
- [ ] **身份认证**
  - 是否使用 JWT 或其他安全的认证机制
  - Token 存储和传输是否安全
  - Token 过期和刷新机制是否完善

- [ ] **权限控制**
  - 是否使用 Guards 进行权限验证
  - 是否实现基于角色的访问控制（RBAC）
  - 敏感操作是否有额外的权限验证

### 数据安全
- [ ] **输入验证**
  - 是否使用 class-validator 进行 DTO 验证
  - 是否验证所有用户输入
  - 是否防止 SQL 注入、XSS 等攻击

- [ ] **敏感数据处理**
  - 密码是否使用 bcrypt 或 argon2 等安全哈希算法
  - 是否避免在日志中记录敏感信息
  - API 响应是否过滤敏感字段

- [ ] **数据加密**
  - 传输层是否使用 HTTPS
  - 敏感数据存储是否加密
  - 加密算法和密钥管理是否安全

### API 安全
- [ ] **速率限制**
  - 是否实现 API 速率限制（throttling）
  - 是否防止暴力破解攻击
  - 是否实现请求签名验证

- [ ] **CORS 配置**
  - CORS 配置是否严格
  - 是否避免使用 `*` 作为允许的源

- [ ] **安全头**
  - 是否设置安全相关的 HTTP 头（如 Helmet）
  - 是否禁用不必要的 HTTP 方法

## 最佳实践

### NestJS 特性
- [ ] **装饰器使用**
  - 是否正确使用 NestJS 装饰器（`@Controller`、`@Get`、`@Post` 等）
  - 自定义装饰器是否遵循 NestJS 约定
  - 装饰器是否可复用

- [ ] **中间件**
  - 中间件使用是否合理
  - 中间件执行顺序是否正确
  - 是否避免在中间件中处理业务逻辑

- [ ] **拦截器与管道**
  - 拦截器是否用于横切关注点（日志、转换等）
  - 管道是否用于验证和转换
  - 是否正确处理异常

### 配置管理
- [ ] **环境配置**
  - 是否使用 `@nestjs/config` 管理配置
  - 敏感配置是否使用环境变量
  - 是否提供配置验证

- [ ] **配置分层**
  - 是否区分开发、测试、生产环境配置
  - 配置是否易于维护和更新

### 日志记录
- [ ] **日志策略**
  - 是否使用 NestJS Logger 或集成专业日志库（Winston、Pino）
  - 日志级别使用是否合理
  - 是否记录关键操作和错误

- [ ] **日志格式**
  - 日志格式是否结构化（JSON）
  - 是否包含必要的上下文信息（请求 ID、用户 ID 等）
  - 是否避免记录敏感信息

### API 设计
- [ ] **RESTful 设计**
  - API 是否遵循 RESTful 原则
  - HTTP 方法使用是否正确（GET、POST、PUT、DELETE 等）
  - 资源命名是否使用名词复数形式

- [ ] **版本控制**
  - API 是否实现版本控制
  - 版本策略是否清晰（URL 版本、Header 版本等）

- [ ] **响应格式**
  - 响应格式是否统一
  - 是否包含必要的元数据（分页、时间戳等）
  - 错误响应是否包含有用的调试信息

## 测试覆盖

### 单元测试
- [ ] **测试覆盖率**
  - 关键业务逻辑是否有单元测试
  - 测试覆盖率是否达到目标（建议 > 80%）
  - 是否使用 Jest 作为测试框架

- [ ] **测试质量**
  - 测试用例是否独立且可重复
  - 是否正确使用 mock 和 stub
  - 是否测试边界条件和异常情况

### 集成测试
- [ ] **端到端测试**
  - 关键 API 是否有集成测试
  - 是否使用 `@nestjs/testing` 模块
  - 数据库测试是否使用测试数据库或事务回滚

- [ ] **测试数据管理**
  - 测试数据是否隔离
  - 是否在测试前后清理数据
  - 是否使用工厂模式生成测试数据

### 测试维护
- [ ] **测试可维护性**
  - 测试代码是否清晰易懂
  - 是否避免测试代码重复
  - 测试是否随着代码变更及时更新

## 审查评分标准

每个检查项可以按以下标准评分：

- **通过（✓）**：完全符合要求
- **部分通过（⚠）**：基本符合但有改进空间
- **未通过（✗）**：不符合要求，需要修复

### 整体评分计算

- **优秀**：90% 以上检查项通过
- **良好**：75%-90% 检查项通过
- **合格**：60%-75% 检查项通过
- **需改进**：低于 60% 检查项通过

## 使用说明

1. **审查前准备**
   - 确保代码已通过本地构建和测试
   - 了解项目背景和业务需求
   - 准备好相关文档和规范

2. **审查过程**
   - 逐项检查清单内容
   - 记录发现的问题和建议
   - 对问题进行分类和优先级排序

3. **审查后**
   - 编写审查报告
   - 与开发团队沟通审查结果
   - 跟踪问题修复进度
